# Research: Prompt 3 – BMT Brand Identity & Premium UX

## 1. Shared Brand System

**Decision**: Use one semantic BMT design system across dashboard, client, and driver apps.

**Rationale**: The platform is operationally connected, and fragmented UI language would reduce trust, comprehension, and product recognition.

**Alternatives considered**:
- Separate visual themes per app
- Feature-specific styling per screen family
- Lightly branded default Material styling

## 2. Color and Theme Strategy

**Decision**: Build the palette around a deep primary base, a transport-forward secondary color, and a restrained accent color with semantic states layered on top.

**Rationale**: Transportation workflows need calm, high-trust visuals with strong operational contrast. Semantic colors must remain easy to scan without overpowering the map or card hierarchy.

**Alternatives considered**:
- High-saturation brand colors
- Monochrome enterprise styling
- A pure dark-mode-first visual system

## 3. Typography Strategy

**Decision**: Use a premium multilingual typography system that supports Arabic and Latin content with consistent hierarchy and strong numeric legibility.

**Rationale**: BMT screens mix operational metadata, route names, times, and status values. Readability and bidirectional consistency matter more than decorative type personality.

**Alternatives considered**:
- Separate typography per language
- Highly stylized display fonts
- Default platform typography without hierarchy tuning

## 4. Map Styling Strategy

**Decision**: Treat the map as a branded transport surface with custom route emphasis, custom vehicle markers, and minimal irrelevant clutter.

**Rationale**: A generic map would hide the product’s identity and weaken route comprehension. The map must read like part of BMT, not an embedded utility.

**Alternatives considered**:
- Default map styling with standard pins
- Heavy geographic detail and decoration
- Map overlays that vary by screen without a shared style system

## 5. Motion Strategy

**Decision**: Use restrained motion for hierarchy changes, selection feedback, route progression, and sheet transitions.

**Rationale**: The product is operational. Motion should support comprehension and premium feel, not create distraction or slow decision-making.

**Alternatives considered**:
- High-energy micro-interactions
- Playful motion patterns
- Static UI with no motion language

## 6. Reusable Operational Components

**Decision**: Standardize captain cards, stop cards, route info components, buttons, chips, badges, sheets, and dialogs as a shared system.

**Rationale**: These surfaces recur across many workflows. Shared components reduce cognitive load and keep BMT visually coherent.

**Alternatives considered**:
- One-off screen-specific layouts
- Different component treatments per app
- Rebuilding each workflow independently

## 7. Accessibility and Responsiveness

**Decision**: Make accessibility and responsive behavior part of the base system, not a later adjustment.

**Rationale**: The platform is used in fast-moving, high-stakes contexts and must remain readable across phone, tablet, desktop, light/dark, Arabic/Latin, and reduced-motion conditions.

**Alternatives considered**:
- Retroactive accessibility cleanup
- Mobile-only layout assumptions
- Theme-specific visual tweaks without semantic consistency
